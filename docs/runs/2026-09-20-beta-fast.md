not Burn), no other GPU job running (confirmed via `pgrep` before every run).
Commit before this session's changes: `10c704e` (merge of `main`@`e8fae27`

Scope: this doc covers the same `t0-beta` checkpoint documented in

## Bug found and fixed

`crates/t0-fast` hardcoded `HEAD_DIM: u32 = 64` in two places: a Rust
constant in `crates/t0-fast/src/model.rs` (sizing `RmsQkDims`/`RopeDims`
uniforms, the attention softmax scale, and `RopeTables::new`), and a WGSL
shader constant `const HEAD_DIM: u32 = 64u;` in
`crates/t0-fast/src/shaders/attention.wgsl` (indexing the fused QKV buffer
via `head * HEAD_DIM` offsets). This is correct for t0-alpha
(512/8=64) but wrong for t0-beta (1024/8=128) — before the fix,
`t0-cli parity --backend fast` on beta failed immediately with
`Error: t0-fast Phase A hardcodes head_dim=64, config gives 128`.

Fix: removed the `HEAD_DIM` constants; `model.rs` now computes
`head_dim = embed / heads` at each call site (`forward_async`,
`attention()`) and threads it into `rmsnorm_qk()`/`rope()` (their uniform
structs already had a `head_dim` field, just weren't receiving a real
value). `attention.wgsl` now computes `let head_dim = dims.embed /
dims.heads;` at the top of `main()` instead of using a compile-time
constant. `rope.wgsl` and `rmsnorm_qk.wgsl` needed no changes — they were
already fully driven by their `Dims` uniform's `head_dim` field.

Also added a `t0-cli drift --backend fast` path (`cmd_drift_fast` in
`crates/cli/src/main.rs`): the existing `drift` subcommand only drove the
Burn `ndarray`/`wgpu` backend. `cmd_drift_fast` reuses the same
synthetic-case methodology as `cmd_drift` (54 cases, seed 42, `t_ctx=512`,
`horizon=96`) but forecasts through `t0_fast::forecast` for both the F32
and GGUF-resident quantized model, using two separate `t0_fast::Engine`
instances (one per model) — `t0_fast::model::linear()` uses a
differently-sized uniform struct for F32 weights (`LinearDims`, 16 bytes)
vs quantized weights (`LinearQDims`, 32 bytes), and `Pool::uniform`
(`crates/t0-fast/src/pool.rs`) never grows an already-allocated buffer for
a given cache key, so sharing one pool's keys between the two models
overran the smaller allocation with a wgpu validation panic.

Regression check: re-ran `t0-cli parity --backend fast --fast-quant f32`
on the existing 3 t0-alpha fixtures after the fix — worst max-abs
unchanged at `1.251698e-6` (identical to the pre-fix baseline recorded in
`docs/runs/2026-09-20-perf.md`), confirming no numerical change for alpha.

## Observations

Beta (embed_dim 1024, 256M params) now runs end-to-end on t0-fast, where
it was previously blocked entirely by the `HEAD_DIM=64` hardcode.

Beta's F32 parity gate passed at 3.218651e-6 worst-case max-abs error,
well inside the 1e-4 gate and the same order of magnitude as alpha's
1.251698e-6.

Beta's drift on t0-fast matches the CPU/Burn reference path
(`docs/runs/2026-09-20-beta.md`) to 3 significant digits for both Q8_0
(0.2047% vs 0.2046% mean-drift-worst) and Q4_0 (2.5494% vs 2.5493%),
indicating t0-fast's quantized kernels introduce no additional drift
beyond what the reference quantization recipe already has.

Beta's single-forecast native latency is roughly 2x-2.1x alpha's at the
same context/horizon: Q8_0 219.2922ms vs 102.5555ms = 2.14x; Q4_0
145.2537ms vs 73.1752ms = 1.99x.

Batch-24 per-signal latency is not the same between alpha and beta: it is
roughly 2.35x-2.38x higher for beta (Q8_0 54.6319ms vs 22.9002ms = 2.39x;
Q4_0 54.5032ms vs 22.9805ms = 2.37x).

Beta's Q8_0 vs Q4_0 GGUF sizes (275.3 MB vs 149.5 MB) are already
documented in `docs/runs/2026-09-20-beta.md`, cited above rather than
re-derived.

Separately, `docs/BENCHMARKS.md`'s existing alpha row also reports
*browser* (Chromium-for-Testing WebGPU) single-forecast warm latency of
Q8_0 34.5ms / Q4_0 29.8ms. That is a different measurement (browser, not
native) from anything run this session — this session's alpha/beta
comparison is native-CLI-vs-native-CLI only (102.6ms/73.2ms alpha vs
219.3ms/145.3ms beta). The browser numbers are not placed in the same
table as the native numbers here, and no ratio is computed between them.
