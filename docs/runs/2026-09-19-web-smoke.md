## Update (same session): windowed instrument, debounced/drag forecasting

Owner feedback after testing the page live: rewired the instrument's
interaction and rendering, still plain JS / no build step / no libraries.
`web/index.html` and `web/worker.js` changed; `scripts/headless/run.mjs`
extended with new gates. Commit: see `git log` (this doc's commit).

- **STATUS log**: keyed lines (`forecast`, `download`, `load`, `series`,
  `backend`) update in place on repeat instead of appending one line per
  event; the box is a fixed-height (108px) scrollable region, capped at 200
  lines, newest at the bottom. Download-percent spam and per-forecast
  timing no longer flood the log.
- **No forecast per slider tick**: the slider's `input` event (and
  chart/strip `pointermove` while dragging) only moves the origin marker
  and updates the label — no `worker.postMessage`. A forecast is only
  requested on slider `change` (release) or pointer-up on the chart/strip,
  debounced 150ms, with a `requestId` so a stale in-flight result can never
  overwrite a newer one.
- **Windowed chart**: the canvas shows the trailing 160 context points plus
  the 32-step horizon (~192 points), not the whole 7305-point series. The
  model still receives up to the full 512-point capped context — only the
  *display* is windowed. A thin (40px) two-tone strip under the chart shows
  where that window sits in the whole series; the strip (and the slider)
  are the whole-series navigators, the chart itself is for fine scrubbing
  within the current window.
- **Rendering**: devicePixelRatio-aware canvas sizing, light gridlines with
  y-axis value labels and month x-ticks, black 1.5px history line, dashed
  vertical origin line with a hollow circle, 2px dark-gray median forecast
  line, light-gray Q10–Q90 fill (+ a second, lighter Q25–Q75 fill from the
  5 trained quantile levels), dashed mid-gray actual-continuation line.
  Legend row: `— Actual  — Forecast  ▮ Q10–Q90` (left) /
  `MAE <v>  sMAPE <v>%  LATENCY <ms>` (right, computed against the real
  continuation), hint line below. No colors beyond the existing gray family
  CSS variables.
- **Series**: still `us_births` (daily), now presented as `series: US
  births · daily` with a link to `web/data/README.md`. A second,
  higher-frequency series (hourly `electricity` from the GIFT-Eval subset)
  was **not** added: only a daily (`D`) and weekly (`W`) snapshot of that
  GIFT-Eval config are already downloaded locally
  (`~/Code/idle-intelligence/models/data/gift-eval/electricity/{D,W}`); an
  hourly cut isn't one flag away from `tools/gifteval_subset.py`'s existing
  exports (it would need a fresh, larger HF dataset download), so it's
  skipped this session rather than done partially.

New headless gates (`scripts/headless/run.mjs`): a real Playwright mouse
drag on `#chart` (`pointerdown` at 30% width, five `pointermove` steps to
55%, `pointerup`) must produce **exactly one** accepted forecast
(`window.__app.forecastCount` delta), not one per move; MAE/sMAPE read from
the DOM must be finite at every tested origin; five `input` events on the
slider (no `change`) must leave `window.__app.logLineCount()` unchanged.

## Reading the numbers

- Page ready (WASM module fetch + model download + GGUF parse/dequant +
  tensor build + series fetch) in ~0.76s — all over loopback, so this is
  not a real-network download time, just a correctness/wiring check.
- Per-forecast latency (context capped at 512, horizon 32, same shape as
  `docs/BENCHMARKS.md`'s native CPU latency table): 592-611 ms in the
  browser's single-threaded WASM vs 363-424 ms native (ndarray, 8 threads)
  for the same quant (Q8_0) — see `docs/runs/2026-09-19-latency-cpu.md`.
  Slower is expected: `burn-ndarray`'s matmul path and this crate's build
  have no WASM SIMD/threading enabled yet, and native ndarray gets to use
  all 8 logical cores. Not investigated further this session (out of
  scope: WebGPU is the intended fast browser path, not a faster CPU-WASM
  build — see `crates/t0-wasm/README.md`).
- Latency is flat across the three tested origins (599.9, 610.9, 592.4 ms)
  because all three (500, 3600, 7000) sit far enough into the series that
  context is already saturated at the 512-point cap
  (`ctxStart = max(0, origin - 512)`, `web/worker.js`); unlike the earlier
  640-point synthetic series, this real 7305-point series makes the
  "partial vs full context" transition (origin < 512) a small fraction of
  the whole slider range, so it wasn't hit by this run's three sample
  origins. Not a regression, just a different sampling of the same cost
  model.
