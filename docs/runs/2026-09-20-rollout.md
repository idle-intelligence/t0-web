## Follow-up session: the stall diagnosed, two bugs fixed, long fixture green

Diagnosed by reading `forecast_rollout` rather than re-running the
23-minute repro: both `t0_core::model::forecast_rollout`
(`crates/t0-core/src/model.rs`) and `t0_fast::forecast_rollout`
(`crates/t0-fast/src/lib.rs`) round `horizon` up to a whole patch
(`round_up(remaining, patch_size).min(MAX_HORIZON)`), which can exceed
`remaining` on the final AR block -- with this fixture's numbers,
`remaining = 176`, `patch_size = 32` gives `horizon = 192`. The very next
line, `remaining -= horizon`, is a plain `usize` subtraction: 176 - 192
underflows. Release builds have `overflow-checks` off by default, so this
doesn't panic -- it silently wraps `remaining` to `usize::MAX`, turning the
`while remaining > 0` loop into a runaway that keeps computing AR blocks
against an ever-growing `paths_context` buffer forever. That matches the
symptom exactly: ~3% CPU over 23+ minutes reads like thrashing (unbounded
`Vec` growth, GPU submission/readback overhead per iteration dwarfing any
real compute), not a genuine stall or legitimately slow compute. Fixed in
both crates with `remaining = remaining.saturating_sub(horizon)` (commit
`4979e48`) -- the final `out.truncate(prediction_length * n_query)` already
discards the overshoot, so saturating at 0 is exactly correct, not a
workaround.

Standard 3-fixture parity on `--backend fast --fast-quant f32` after the
fix: still 1.25e-6-class (`case0` 8.34e-7, `case1` 1.25e-6, `case2`
1.22e-6), confirming no regression. `parity --long --backend fast`:


### Second bug, found while exercising `--backend fast` on gifteval

Running the official-protocol gifteval subset (many windows of varying
context length through one resident `GpuModel`, see
`docs/runs/2026-09-20-official-protocol-fast.md`) surfaced a second,
unrelated bug: `t0-fast/src/model.rs`'s `linear()` picks between a naive
and a tiled kernel based on `rows >= TILED_THRESHOLD_ROWS` (32), but its
`Pool::bind_group` cache key didn't include which one was picked. Naive
and tiled are different `wgpu::ComputePipeline`s, and since both use
`layout: None` (auto-derived bind-group layouts), each pipeline gets its
own distinct `BindGroupLayout` object even though the WGSL bindings are
structurally identical. A call site whose `rows` crosses the threshold in
both directions across separate forward calls (any two gifteval windows on
opposite sides of 32 patches, going through the same `GpuModel`) could
therefore reuse a bind group built against the *other* pipeline's layout.
wgpu doesn't reject this at `set_bind_group()` time -- it poisons the
encoder and only reports "Encoder is invalid" at `.finish()`, several
calls later, which is why this looked at first like a crash in an
unrelated window. Every earlier fixture/bench (the 3 standard fixtures,
the long-rollout fixture, `bench --signals N`) kept `rows` on one side of
the threshold for its entire run, so this never fired before gifteval's
mixed-length windows. Fixed by suffixing the bind-group cache key with
`tiled`/`naive` (commit `f2cf870`); standard + long-fixture parity
reconfirmed unchanged after the fix (same numbers as above).
