## What's blocking

Nothing structural -- `forecast_rollout` compiles, is unit-tested at the
quantile-math level, and the fixture is real. The blocker is wall-clock:
`ndarray` is impractically slow for this shape, and the `wgpu` backend
(expected far faster per this repo's own benchmark history) has not been

## wgpu attempt (Metal, M2)

```
cargo run -p t0-cli --release --no-default-features --features wgpu -- parity --long --backend wgpu \
  --weights .../t0-alpha/model.safetensors --config .../t0-alpha/config.json
```

Loaded in 0.233s, then panicked before printing any case line (35.9s wall
including the release build):

```
thread 'main' panicked at cubek-matmul-0.1.1/src/launch/strategy.rs:437:22:
called `Result::unwrap()` on an `Err` value: Unable to launch matmul because
the config is invalid: "This algorithm needs 40960 shared memory bytes but
hardware limit is 32768."
```

This is the same cubecl-wgpu autotune bug already documented in
`docs/runs/2026-09-19-milestone1a.md` and worked around in
`forecast_batch`/`DEFAULT_BATCH_CHUNK` for the *batch/n_signals* dimension
(chunks of 16) -- but here it fires on `forecast_rollout`'s very first
single-window call (`forecast`, `v=1`, `t_ctx=4096`, `horizon=1024`, no
batching involved), so the trigger is `p` (patches attended jointly in a TIME
layer: `(4096+1024)/32 = 160` here, vs <=19 in every fixture that's worked so
far) rather than `n_signals`. The existing chunk-by-signals mitigation does
nothing for this: there is only one signal in this call. Not something to
patch blind in this session -- per the 2026-09-19 doc, the real fix is a
cubecl-wgpu version bump or a workgroup-size override upstream, both out of
scope here.

**Per the gate this session was given ("if wgpu passes < 1e-4, implement
--backend fast next"): wgpu did not pass -- it crashed before producing a
number -- so `--backend fast` rollout, `parity --long --backend fast`, and
the official-protocol subset run were not attempted.**
