# CPU (ndarray) build: enabling WebAssembly SIMD

Machine: Apple M2 (Darwin 25.3.0), Playwright's bundled Chromium-for-Testing
`chromium-1243` (Chrome for Testing 153.0.8010.12), headless (valid for a
CPU-only measurement). wasm SIMD (`simd128`) is enabled by default in this
Chromium build, no flags needed.

## Setup

Before this change, `.cargo/config.toml` only set
`--cfg getrandom_backend="wasm_js"` for `wasm32-unknown-unknown`; no
`target-feature` flags. `crates/t0-wasm`'s CPU path is `burn-ndarray` ->
`ndarray` -> `matrixmultiply`; none of these expose a Cargo feature named
`simd`/`simd128` (`cargo tree -p t0-wasm --target wasm32-unknown-unknown
-e features` shows only unrelated `simd` features on `zerocopy`/
`miniz_oxide`/`ppv-lite86`, pulled in by getrandom/flate2, not by the
matmul path). `matrixmultiply`'s wasm SIMD kernels are gated purely on the
compile-time `target_feature = "simd128"` cfg, so the only change needed
is the rustc flag, not a Cargo feature.

Change: added `"-C", "target-feature=+simd128"` to the existing
`rustflags` array in `.cargo/config.toml`. This applies to every
`wasm32-unknown-unknown` build in the workspace, including the `fast`
(WebGPU, `crates/t0-fast`) build; `wasm-pack build crates/t0-wasm --target
web --out-dir pkg-fast --release --no-default-features --features fast`
still builds clean with the flag in place.

v128 instruction count checked with `wasm-tools print <file> | grep -c
v128` (`wasm-tools` installed via `cargo install wasm-tools`).

## Commands

```
wasm-pack build crates/t0-wasm --target web --out-dir pkg-simd --release
wasm-pack build crates/t0-wasm --target web --out-dir pkg-fast --release --no-default-features --features fast
cargo test -p t0-core --release
```

Benchmark harness: a page outside the repo
(`~/.claude/jobs/f13f376f/tmp/bench.html`, served via a gitignored/
untracked symlink at the repo root so `python3 -m http.server` could serve
both it and `/web/...` assets) that imports a given `pkg` dir, awaits
`initBackend()`, loads `web/models/alpha-q4/t0-alpha-q4_0.gguf`, builds a
512-point context from `web/data/series.f32[3088:3600]`, then times
`forecast(ctx, 32)`: 3 warm-ups, then 10 timed calls (median, p90), driven
headlessly with the repo's own `node_modules/playwright`.

## Results

| build | v128 count | wasm size (bytes) | median (ms) | p90 (ms) |
|---|---|---|---|---|
| `web/pkg` (baseline, no simd128) | 0 | 1,443,817 | 533.2 / 542.1 / 566.3 (3 runs) | 547.0 / 567.0 / 583.5 |
| `crates/t0-wasm/pkg-simd` (with simd128) | 16,204 | 1,536,755 | 233.2 / 239.0 / 250.2 (3 runs) | 235.6 / 246.6 / 259.8 |

Speedup: 2.26x-2.29x across the three alternating run pairs (median
baseline / median simd128 each time). wasm size grew 6.4% (1,443,817 ->
1,536,755 bytes) from the wider SIMD kernel variants.

Agreement: max abs difference across all 160 output values (horizon 32 x
n_quantiles 5) between `web/pkg` and `crates/t0-wasm/pkg-simd` was 0.0
(bit-identical in this run). Against the WebGPU (`fast`) build
(`crates/t0-wasm/pkg-fast`, also built with the simd128 flag in place, run
headless with `--enable-unsafe-webgpu`): max abs diff 0.00146484375
against both CPU builds, consistent with ordinary float rounding
differences between backends, not a correctness issue.

## Native sanity

`cargo test -p t0-core --release`: all non-ignored tests pass (4 passed,
2 ignored — the 2 ignored tests require a local checkpoint download,
unrelated to this change). No change expected or observed.

## Shipping the CPU build with SIMD

`.cargo/config.toml` is committed and applies to every
`wasm32-unknown-unknown` build, so `tools/publish-pages.sh`'s existing
`wasm-pack build crates/t0-wasm --target web --out-dir pkg --release`
line needs no change: rebuilding to `crates/t0-wasm/pkg` (the exact
command the script runs) was checked directly and produces 16,204 v128
instructions, the same as `pkg-simd`.

## Browser support

wasm SIMD is supported in Chrome 91+, Firefox 89+, Safari 16.4+. On a
browser without it, `WebAssembly.instantiate` throws inside
`handleLoad()`'s `await t0wasm.default(...)` call in `web/worker.js`.
That call already runs inside the top-level `self.onmessage` try/catch
(`web/worker.js`), which posts `{ type: 'error', message: ... }`;
`web/index.html`'s `case 'error':` handler sets the status dot to
`error` and shows `Error: <message>` in the status line. A visitor on an
old Safari would see that error message, not a blank page. No code
change needed here.
