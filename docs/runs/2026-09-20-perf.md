### Item 1: `RuntimeOptions.tasks_max` — tried, reverted

Read `cubecl-wgpu-0.9.0/src/runtime.rs` and `compute/stream.rs`: default
`tasks_max` (`RuntimeOptions::default()`, non-test build) is **32**, not
"small" as the task brief assumed — `t0-wasm`'s existing
`init_setup_async::<WebGpu>(&device, Default::default())` call already
gets that. More importantly, `Stream::enqueue_task`'s `Write` arm
(`stream.rs:100-103`) calls `self.flush()` unconditionally *before every
buffer write*, independent of `tasks_max` — so the per-forecast forced
flushes measured in the first follow-up session (~35, per the GPU-busy/
idle trace) are dominated by buffer-upload flushes, not by hitting the
32-task cap. This makes `tasks_max` a wrong lever for this workload:
raising it only changes how many *matmul/elementwise* dispatches get
batched between those forced write-flushes, and batching more encoding
into one pass before submission means the GPU sits idle longer waiting
for the CPU to finish encoding, which showed up as a real regression:

| tasks_max | cold ms (3 runs) | warm median ms (3 runs) | batch ms/signal (3 runs) |
|---|---|---|---|
| 32 (default, baseline) | 390.8 / 481.1 / 508.7 | 169.9 / 173.6 / 172.5 | 36.17 / 38.29 / 38.19 |
| 4096 | 1417.2 / 1119.3 / 1066.1 | 225.1 / 230.4 / 230.1 | 43.12 / 41.58 / 42.88 |

Cold ~2.5x worse, warm ~+35%, batch ~+12% — consistently worse across 3
repeats each, not noise. **Reverted** (never committed; working tree
confirmed clean of this change before moving to item 2).

### Item 2: per-forecast `Tensor::from_floats` writes — RoPE-table caching kept, masks left alone

Re-read `crates/t0-core/src/model.rs`'s `forward_tensor` against this
task's "hidden syncs" checklist (`Tensor::from_data`/`from_floats` per
call). Found 6 `from_floats` GPU buffer writes per forecast, none flagged
by the prior session's audit (which only checked for `.into_data()`/
`.into_data_async()` calls, not buffer *writes*): `concat_t` (patch
encoder input), `type_emb`'s one-hot (`gather_rows`), `time_mask`,
`group_mask`, and `RopeTables::new`'s `cos`/`sin`/`scale` (3 writes) — each
one forces a `stream.flush()` first (`cubecl-wgpu`'s `ScheduleTask::Write`
handling, see item 1). Of these, only the RoPE tables are a pure function
of shape (`p` = patch count, `head_dim` from config) and not of per-call
series data (masks depend on `group_ids`/`variate_type`/missing-value
mask, which can vary call-to-call in general use even though this bench
harness reuses the same series) — so only `RopeTables` is safe to cache
without risking stale output on a data change.

Change: `T0Model<B>` gained a `rope_cache: RefCell<Option<(usize,
RopeTables<B>)>>` field (keyed by `p`), populated on first use and reused
whenever a later call has the same `p` (`crates/t0-core/src/model.rs`);
`RopeTables` derives `Clone` (`crates/t0-core/src/ops.rs`) so the cached
tables can be handed out without re-uploading. Single-threaded borrow,
released before any `.await`, no reentrancy (`forecast_batch_chunked_async`
processes chunks sequentially, confirmed by reading it — no concurrent
`forward_tensor` calls exist in this codebase). This removes 3 of the 6
forced write-flushes on every repeat call at a fixed context length (the
common case: one model, one series length, called in a loop).

**Parity**: `t0-cli parity --backend ndarray` against `t0-alpha` F32
weights, all 3 fixtures — worst quantile max-abs unchanged at
**1.192093e-6**, PASS (identical to pre-change, as expected: same values,
just fewer redundant uploads of them).

**Measured effect**: within noise of baseline, not a measurable win:

| | cold ms (3 runs) | warm median ms (3 runs) | batch ms/signal (3 runs) |
|---|---|---|---|
| baseline (no rope cache) | 390.8 / 481.1 / 508.7 | 169.9 / 173.6 / 172.5 | 36.17 / 38.29 / 38.19 |
| with rope cache | 1810.4* / 503.5 / 494.7 | 172.3 / 173.1 / 173.6 | 54.80* / 38.71 / 38.80 |

(*run 1's cold/batch numbers are outliers — first Chromium launch after a
background build finished, not reproduced in runs 2-3 or in any other
condition; runs 2-3 match baseline closely.) This null result is
consistent with the first follow-up session's GPU-busy/idle trace: each
flush costs ~210-220us of submission overhead, so removing 3 of ~35
flushes/forecast saves on the order of 0.6ms against a 170ms warm call —
below this harness's run-to-run noise floor (~3-4ms). **Kept anyway**:
it's a correct, harmless de-duplication (verified by the parity gate) that
directly answers this task's "hidden syncs" checklist item, even though it
doesn't move the needle — the actual cost, as the first follow-up session
already established, is per-dispatch launch/sync latency (JS event loop +
IPC + driver submission), not the number of buffer uploads or the task-batching
cap.

### Step 2: custom fused f32 linear kernel — implemented, measured, reverted

Ported the dispatch mechanism from
`../llm-web/crates/llm-wasm/src/gguf.rs`
(`KernelSource`/`SourceKernel`/raw `cubecl::server::{Bindings, CubeCount}`
bindings launched via `client.launch(...)` alongside Burn tensors, same
pattern as that crate's `rmsnorm_fused`/`matmul_tiled_f32`): a naive
one-thread-per-output-element WGSL kernel (`out[m,n] = dot(x[m,:],
w[n,:]) + b[n]`, `w`'s PyTorch `[out,in]` layout needs no transpose)
fusing the matmul and bias-add `ops.rs`'s `linear()` currently does as two
separate Burn ops, gated to `m <= 32`. Wired in via a new `LinearKernel`
trait (`ops.rs`) with a default no-op fallback and a real impl for
`burn::backend::Wgpu<f32, i32>`, propagated through `residual_block`/
`swiglu_ffn`/`mhsa`/`T0Model`'s generic bounds; `t0-core` gained optional
`ndarray`/`wgpu` features forwarding from `cli`'s and `t0-wasm`'s existing
features.

**The blocker this task brief didn't anticipate**: this repo's
`burn-wgpu` dependency has the `fusion` feature on (`eba8c52`, kept —
batch-24 win), so `burn_wgpu::Wgpu<f32,i32>` is `burn_fusion::Fusion<
CubeBackend<WgpuRuntime,f32,i32,u32>>`, not a bare `CubeTensor`-backed
type the way llm-web's (fusion-off) `Wgpu` is. `x.into_primitive().tensor()`
yields a `FusionTensor`, not the `CubeTensor` the raw-kernel dispatch
needs. Bridged both directions using `burn_fusion`'s own public API (same
pattern its `FloatTensorOps::float_from_data` impl uses internally,
`burn-fusion-0.20.1/src/ops/tensor.rs`): `FusionClient::resolve_tensor_float::<Base>`
to drain a tensor's pending fused ops and get the raw `CubeTensor` in
(costs a stream drain per input), then `Base::float_tensor_handle` +
`FusionClient::register_tensor_handle` + `client.register(..,
OperationIr::Init(desc), NoOp::<Base>::new()).output()` to re-enter the
kernel's raw output back into the fusion graph. Required adding
`burn-fusion`/`burn-ir` as direct optional deps to `t0-core` (version
`"0.20"`, unifies with `burn`'s internal copies) since neither is
re-exported through `burn::backend`.

**It compiled and the parity gate still passes** (`t0-cli parity
--backend ndarray` — the kernel is wgpu-only and inert under `ndarray`;
`--backend wgpu` also checked): worst quantile max-abs unchanged at
**1.192093e-6** across all 3 fixtures, identical to the pre-kernel
baseline (expected: same values, different kernel).

**But it is a regression, not a win**:

| variant | warm median, `--signals 1` (5 reps) | `--signals 16 --chunk 16` (3 reps, per-signal) |
|---|---|---|
| baseline (Burn matmul, fusion on) | 223.7 ms | ~34 ms (docs/BENCHMARKS.md, prior session) |
| custom kernel (`m<=32` gate) | **282.7 ms** (+26%) | 40.0 ms (batch never hits `m<=32` at `v=16`: `m = v*p = 272` for every linear call, so this is the unfused matmul path, run-to-run noise not a kernel effect) |

**Why it's slower despite fusing 2 dispatches into 1**: `resolve_tensor_float`
drains the fusion stream synchronously on *every one of the ~3 input
tensors per linear call* (x, w, b) — turning ~170 linear calls/forecast
into ~500+ forced stream drains, each paying the same per-dispatch
launch/sync tax the prior sessions already identified as the dominant
cost (GPU-busy-vs-idle trace: ~210-220us/flush submission overhead, this
task's own "3-4ms/dispatch" fact). The naive kernel's one-dispatch-instead-
of-two saves less than the extra drains cost — fighting Burn's fusion
scheduler by hand-draining around it is net negative, the opposite of
what "fuse more work into fewer dispatches" was supposed to buy. A fix
would need either (a) disabling `fusion` for `wgpu` entirely and doing
*all* dispatch fusion by hand (the per-layer attention block or whole
transformer layer as one kernel, not per-`linear()` calls — item 4 from
the second follow-up session, still not attempted, same multi-hour scope
each prior session deferred it for), or (b) a real Burn-level "custom
fusion op" registration (`burn_fusion::FusionBackend`'s optimization
trait) instead of hand-rolled drain/reinsert around individual ops —
neither fits in this session.

**Reverted**: `git checkout` on `Cargo.lock`, `crates/cli/Cargo.toml`,
`crates/t0-core/Cargo.toml`, `crates/t0-core/src/{lib,model,ops}.rs`,
`crates/t0-wasm/Cargo.toml`; deleted `crates/t0-core/src/kernel_wgpu.rs`
and `crates/t0-core/src/wgsl/`. Rebuilt (`cargo build --release
--no-default-features --features wgpu`) to confirm the tree is back to
the clean pre-session baseline. Never committed.

### Net effect of this session

No code changed (attempt reverted). `docs/BENCHMARKS.md`'s head-to-head
table and paragraph are unchanged and still accurate; no browser rebuild
was done since nothing that would move `bench/ours` numbers survived this
session. What *is* new and worth keeping for the next attempt: hard
numbers that matmul is 85% of the cost (not attention/norms/RoPE — step 3
of this task's brief is moot), that a single tiny matmul's GPU-side cost
is sub-millisecond so the 224 ms/58-dispatch total is essentially all
launch/sync overhead, and that per-op kernel fusion fights Burn's
`fusion` feature rather than complementing it under this backend
configuration — the next attempt needs to fuse at the granularity of a
whole attention block or transformer layer (one dispatch replacing the
~5 dispatches/layer that make up the QKV/attention/wO/FFN chain), not
per-`linear()`-call, to net positive against `fusion`'s own per-call
drain cost.

## Fourth follow-up session: t0-fast, a second forward path with no Burn at inference

Machine: Apple M2 (Darwin 25.3.0). Native measurements via native `wgpu`/
Metal (`t0-cli bench --backend fast`); browser measurements via
Playwright's bundled Chromium-for-Testing (`chromium-1243`),
`scripts/headless/run_ours_bench.mjs` against `bench/ours/index.html`
(`us_births`, origin 3600, context 512, horizon 32, 24-signal batch chunk
16 — same fixture/window as the head-to-head table). `pgrep` contention
check clean before every measurement (no other headless Chromium or
native cargo/wasm-pack job running).

New crate `crates/t0-fast`: raw `wgpu::Device`/`Queue`, ten hand-written
WGSL compute pipelines (`linear`/`linear_q8`/`linear_q4`, `add_inplace`,
`gather_add`, `rmsnorm_full`, `rmsnorm_qk`, `rope`, `attention`,
`transpose_outer`, `silu_mul`, `quantile_head`) reimplementing every

### Phase A (f32, M=1) -- commit `23916b2`

Parity (`t0-cli parity --backend fast`, all 3 fixtures, f32 weights vs
Burn ndarray reference): worst quantile max-abs **1.252e-6**, PASS.
Native bench (context=512/horizon=32/M=1, warm median of 5): **98.7 ms**
vs burn-wgpu's **222.2 ms** same case (2.25x).

### Buffer/bind-group pooling + attention seq cap -- commit `7d38fa0`

`src/pool.rs`: grow-only per-call-site `wgpu::Buffer` cache (uniform
buffers updated via `queue.write_buffer` in place, not recreated),
bind groups cached and invalidated only when the pool's generation
advances (some buffer actually grew). `t0-cli bench --backend fast` now
reports `warm_alloc_count` (pool allocations on the first post-warmup
call) -- **0** at a fixed `(v, p)` shape, confirming grow-once behavior.
Also lifted `attention.wgsl`'s `MAX_SEQ` from 64 to 128 (model max is 32
patches at `max_horizon=1024`/`patch_size=32`; 128 leaves headroom for a
batched forecast's group-attention variate-axis too), one kernel, no
per-call branch on `seq`.

Parity unchanged (1.252e-6). Bench: **96.9 ms** (was 98.7 ms), essentially
flat -- buffer/bind-group allocation was not the dominant cost at this
scale; the near-350-dispatch chain's per-dispatch submission/kernel time
itself is.

### Phase B: Q8_0/Q4_0 resident weights, in-kernel dequant -- commit `7275e97`

`shaders/linear_q8.wgsl`/`linear_q4.wgsl`: same contract as `linear.wgsl`,
weight matrix is Q8_0/Q4_0-resident (t0-core's own block format, QK=32),
dequantized per-element inside the naive per-output-thread loop.
`quant.rs` repacks each block's f16 scale to f32 host-side and the
quantized values 4/u32 so the kernel never decodes f16 or does
byte-addressed storage reads. Only the four big per-layer matmuls (wQKV,
wO, mlp.0, mlp.2) are quantized, matching `t0_core::weights::is_quantizable`.

Two GPU unit tests (`t0-fast::model::tests`) isolate each kernel against a
direct dequant-and-dot reference at K=512: both match to float32 rounding
(~1e-7), confirming the kernels themselves are correct.

Parity: Q8_0/Q4_0 compare against **Burn's own quantized path**
(round-tripped through `Weights::export_gguf`/`load_gguf`, same
`quantize_q8_0`/`quantize_q4_0` fns), not the F32 fixtures -- a lossy
quantization is expected to diverge from F32 truth regardless of
implementation, so the 1e-4 gate only applies to `fast_quant=f32`. Result:
Q8_0 worst max-abs **3.53e-4**, Q4_0 worst max-abs **3.92e-4**, both above
1e-4 but confirmed (via the isolated kernel tests) to be
accumulation-order/depth sensitivity compounding across 24 layers on
*bit-identical* quantized weight values, not a dequant bug -- the F32
Phase A comparison shows the same per-call float-rounding mechanism
compounds to only 1.25e-6 over all 170 linear calls when the weights
aren't quantized, so this is a real (if larger than expected) numerical
sensitivity, not something more debugging turned up a cause for within
this session's budget.

Native bench (context=512/horizon=32/M=1, warm median of 5):

| quant | ms | quantizable_gpu_bytes | ratio vs f32 |
|---|---|---|---|
| f32 | 96.9 | 402,653,184 | 1.000 |
| q8_0 | 101.5 | 113,246,208 | 0.281 |
| q4_0 | 71.1 | 62,914,560 | 0.156 |

Q8_0 is *slower* than f32 despite 3.6x less memory: the naive per-element
dequant loop is compute-bound (8 u32 reads + 32 shift/mask/sign-extend
ops per block), not bandwidth-bound, so the smaller footprint doesn't pay
off. Q4_0 is faster (half the u32 reads/block of Q8_0) -- memory traffic
does matter once the per-element ALU cost is roughly halved.

### Phase C (partial): independent-signal batching -- commit `3aff33c`

`t0_fast::forecast_batch_chunked(_async)`: same
`TimeSeries::from_context_batch` semantics as
`t0_core::forecast_batch_chunked` (each signal gets a distinct group id),
chunked at `DEFAULT_BATCH_CHUNK=16` for a fair comparison with the Burn
baseline's chunking (no shared-memory-autotune limit applies to these
hand-written kernels, so 16 is a benchmarking-parity choice here, not a
correctness requirement).

Native bench, batch-24, chunk 16, warm median of 3:

| quant | ms/signal |
|---|---|
| f32 | 71.25 |
| q8_0 | 59.54 |
| q4_0 | 36.25 |

All three are well above the 8.9 ms/signal target (their ONNX INT8 WebGPU
number). Batching amortizes the fixed ~350-dispatch-per-forecast overhead
across more real work (71.25 ms/signal at batch-24 vs 96.9 ms/signal at
M=1 for f32), but every `linear`/`linear_q8`/`linear_q4` kernel is still
one-thread-per-output-element with zero data reuse across the batch (M)
row dimension -- there is no tiled/shared-memory GEMM variant. That
kernel is the remaining Phase C item and the biggest lever left; not
attempted this session (same multi-hour/correctness-risk scope every
prior session in this doc has deferred it for).

### t0-wasm wiring + real-browser measurement -- not committed as a doc update to BENCHMARKS.md until this entry, wasm build itself is new code

## Fifth follow-up session: GGUF-resident Q8_0/Q4_0 in the browser, tiled GEMM, gifteval --backend fast

Machine: Apple M2 (Darwin 25.3.0). Native via `t0-cli bench --backend fast`
(Metal/wgpu); browser via Playwright's Chromium-for-Testing
(`scripts/headless/run_ours_bench.mjs`, `bench/ours/index.html`,
`us_births` origin 3600, context 512, horizon 32, batch-24 chunk 16 --
same window as every prior session in this doc). `pgrep` contention check
clean before every measurement except one remote `ssh ... cargo build` on
the 3080 box (doesn't touch this M2's GPU, per this repo's own rule).

### Item 1: GGUF-resident loading (commit `7e2bf9b`)

The previous session's Q8_0/Q4_0 path always went through
`t0_fast::load_model` on an in-memory F32 `Weights` (from safetensors),
quantizing the four big matmuls on the fly with `quantize_q8_0`/`_q4_0`.
`t0-wasm`'s browser build called this after `Weights::load_gguf_bytes`
fully dequantized the downloaded GGUF to f32 first -- exactly the
"f32 expansion" the task brief asked to avoid, and (see below) the actual
bug behind last session's inflated parity numbers.

New: `GpuModel::load_from_gguf_bytes` (`model.rs`) reads a GGUF's raw
`(shape, GgmlType, Vec<u8>)` per tensor and, for the four big matmuls,
routes straight to `quant::load_matmul_weight_gguf`, which recognizes
`GgmlType::Q8_0`/`Q4_0` and calls `split_q8_blocks`/`split_q4_blocks`
*on the on-disk block bytes directly* -- no `quantize_*` call, no
intermediate f32 array for those tensors at any point. Small tensors
(patch encoder, decoder, norms, type embeddings -- always F16 on disk per
`export_gguf`'s policy) still dequantize to f32, same as before.
`t0_core::weights::config_from_gguf_metadata` was extracted out of
`Weights::load_gguf_bytes` so both loaders share the metadata parsing.
`t0-wasm`'s `fast.rs` now calls `load_model_from_gguf` instead of the old
roundtrip.

**Parity correction**: comparing against Burn's own quantized path (same
GGUF, loaded via `Weights::load_gguf`), Q8_0 worst max-abs is now
**1.49e-6** and Q4_0 **2.03e-6** -- both far tighter than last session's
3.53e-4/3.92e-4. Root cause, now understood: last session's "Burn
reference" was built by exporting a *fresh* GGUF from the F32 safetensors
(`weights.export_gguf`), which reduces the small tensors to F16 -- while
`t0-fast`'s model (built from the original F32 `Weights`) kept those same
small tensors at full F32. The two sides were comparing different
precisions on tensors that directly gate output precision (patch encoder,
decoder), not "accumulation-order/depth sensitivity" as that session
concluded. This session's GGUF-resident path loads *both* sides from the
*same* GGUF, so the small tensors match exactly and the discrepancy
disappears. (That prior conclusion is superseded; recorded here per this
repo's "code is ground truth over docs" rule -- not deleting the old
entry, correcting it.)

Native bench (context=512/horizon=32/M=1, warm median of 5, from the same
GGUFs as before): Q8_0 101.99ms, Q4_0 71.57ms -- unchanged from the
requantize-from-safetensors path within noise (same GPU compute either
way; only the *load* path changed).

Real-browser WebGPU (before the tiled-GEMM item below): Q8_0 warm 34.6ms
/ batch-24 18.55ms/signal; Q4_0 warm 29.8ms / batch-24 15.42ms/signal.
**Both single-call numbers are already under their ONNX INT8's 64ms** --
a first for this repo. GPU memory (`GpuModel::total_weight_bytes` +
`Pool::resident_bytes`, exposed via a new `T0Wasm.gpuBytes()`, measured
after `benchOne`'s cold + 11 single + 1 batch-24 calls so it reflects the
batch-24 pool's peak, not the single-signal working set): Q8_0 396.9MB,
Q4_0 346.6MB.

**Open question, not resolved this session**: native Q8_0/Q4_0 (102/71ms)
are *slower* than the same engine/quantization in a real browser
(34.6/29.8ms) -- a ~3x gap in the browser's favor for quantized weights,
while the F32-resident row only showed a ~13% browser advantage (84.4ms
browser vs 96.9ms native). Something about Chromium's Dawn/WebGPU-on-Metal
implementation handles this crate's many-small-dispatch chain, or its
packed-u32 quantized buffers specifically, better than the native `wgpu`
crate does on the same hardware. Not chased further this session (would
need a GPU trace comparison of native wgpu vs Dawn, out of scope) --
flagged for whoever picks up the tiled-Q4_0 or the "why is native slower"
threads next.

### Item 2: tiled shared-memory GEMM (commit `7e2bf9b`, same as item 1)

`shaders/linear_tiled.wgsl` / `linear_tiled_q8.wgsl` / `linear_tiled_q4.wgsl`:
classic 16x16-tile GEMM, `x` and `w` tiles both loaded into
`var<workgroup>` shared memory (both operands share a `[rows, K]` layout,
so no transpose is needed -- the accumulate step just reads the `w` tile
"transposed", `b_tile[tx][kk]` instead of `[kk][tx]`), f32 accumulate.
The Q8_0/Q4_0 variants dequantize into the `b_tile` slot once per tile
element instead of once per output thread -- the actual fix for the
missing "M-dimension reuse" every prior session in this doc named as the
biggest lever. `linear()` picks the tiled pipeline when `rows >=
TILED_THRESHOLD_ROWS` (32); six new GPU unit tests (naive+tiled x
f32/Q8_0/Q4_0) all match a direct dequant-and-dot reference to float32
rounding.

Native bench, batch-24, chunk 16, warm median of 3, ms/signal:

| quant | naive (prior session) | tiled |
|---|---|---|
| f32 | 71.25 | **41.16** |
| q8_0 | 59.54 | **41.76** |
| q4_0 | 36.25 | 41.83 (worse -- kept on naive) |

F32 and Q8_0 both win clearly (~40% faster); Q4_0 regresses (measured,
not assumed) -- its dequant is cheap enough (4 bits, no sign-extend
branch) that the naive kernel was never memory-bound, so the tiled
kernel's extra shared-memory/barrier overhead is pure cost with no
saving. `linear()` only routes Q8_0 and F32 to the tiled pipeline;
Q4_0 always uses the naive one (measured decision, see `model.rs`'s
comment at the dispatch site).

Real-browser WebGPU, batch-24, after tiling: Q8_0 18.06ms/signal (was
18.55), Q4_0 15.29ms/signal (unaffected, still naive). Essentially flat
in the browser -- consistent with the "open question" above: whatever
makes the browser path already fast for quantized batches left little
headroom for the tiled kernel to add on top of it, unlike the clear
native win.

Parity after tiling: unchanged (fixtures' trivariate case has 57 rows,
already exercises the tiled path) -- Q8_0 1.49e-6, Q4_0 2.03e-6.

### Item 3: `t0-cli gifteval --backend fast` (commit `c9ce6e3`)

`cmd_gifteval_fast` reuses `cmd_gifteval`'s exact data path (same
`fixtures/gifteval` manifest/windows, same per-window loop), driven by
`t0_fast::forecast` against a GGUF-resident model. This fills this repo's

Ran both quants through `t0-cli gifteval --backend fast` +
