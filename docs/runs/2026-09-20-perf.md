# WebGPU perf: closing the gap vs their ONNX INT8

Machine: Apple M2 (Darwin 25.3.0), Playwright's bundled Chromium-for-Testing
`chromium-1243`. Same `bench/ours` harness as
`docs/runs/2026-09-20-head-to-head.md` (`us_births`, origin 3600, context
512, horizon 32, Q8_0 WebGPU unless noted). GPU-contention rule checked
before every measurement (`pgrep` for headless Chromium / native wgpu jobs
on this M2; a remote `ssh ... cargo build` on the 3080 box and static
`http.server`/`jacobi-serve.mjs` processes were running but do not touch
this machine's GPU).

## Step 1: profile before changing anything

CDP `Tracing.start`/`end` (`disabled-by-default-devtools.timeline`, `gpu`,
`blink.user_timing`), 3 warmup forecasts before tracing (so shader
compile/autotune isn't in the traced window), one trace per case
(`scripts/headless/trace_ours.mjs`, `bench/ours/index.html`'s new
`window.__bench.{warmup,oneForecast,oneBatch}`). Raw traces:
`~/.claude/jobs/f13f376f/tmp/t0-trace-{single,batch}.json`.

| case | wall time (user_timing measure) | `GpuChannel::Flush` count (proxy for GPU command-buffer submissions) | readback/`MapAsync` events |
|---|---|---|---|
| single warm forecast | 170.0 ms | 58 | 0 (not captured by these categories — see caveat) |
| 24-signal batch (chunk 16, 2 chunks) | not isolated separately this run | 122 (~58-64/chunk, consistent with single) | 0 |

**Caveat on the readback count**: the `gpu`/`devtools.timeline`/
`blink.user_timing` CDP categories used here don't surface WebGPU
`mapAsync`/buffer-readback events by name (nothing matching
`MapAsync|BufferMap|readback` appears in either trace) — this is a gap in
the category set, not evidence there are zero readbacks. Code-level check
instead: `crates/t0-core/src/model.rs`'s `forward_async` calls
`out.into_data_async().await` exactly once, on the single final `[v, p,
patch_size, n_q]` tensor, and nothing upstream in `forward_tensor` calls
`.into_data()`/`.into_data_async()` — confirmed by reading the whole
forward path (patch encoder -> per-layer attention/FFN -> out-norm ->
decoder -> quantile head), so there is exactly one readback per forecast
call by construction, matching the target in this task's brief.

**Dispatch fragmentation**: ~58 GPU command-buffer flushes for one
forward pass (12 transformer layers per `config.json`, so ~4-5 flushes/
layer: qkv projection, attention matmuls, output projection, 2 FFN
matmuls, elementwise/softmax/norm ops each apparently submitting their own
command buffer — no operator fusion is compiled in, `burn-wgpu`'s
`fusion` feature is off because this repo's `Cargo.toml` sets
`default-features = false` on `burn-wgpu`, which also strips `fusion` from
burn-wgpu's own `default` feature list). This matches the task brief's
named hazard (~800 dispatches/step would be ~5x slower; here it's ~58/
forecast, in the same fragmentation regime, not the AR-decode case but the
same mechanism) — items below try to reduce it.

## Step 2: changes tried

| change | cold ms | warm ms | batch-24 ms/signal | `GpuChannel::Flush` count/forecast | kept? |
|---|---|---|---|---|---|
| baseline (this session start, matches `docs/runs/2026-09-20-head-to-head.md`) | 707.1 | 162.5 | 46.07 | 58 (single) / 122 (batch-24, 2 chunks) | — |
| (a) `burn-wgpu`'s `fusion` feature (`Cargo.toml`'s workspace `burn-wgpu` dep: `default-features = false` had also silently stripped `fusion` out of burn-wgpu's own `default` feature list, since this repo lists no explicit features — added `features = ["fusion"]` back) | 296.7-310.0 | 169.3-169.8 | 33.98-34.22 | 105 (single) / 210 (batch-24) — **higher**, not lower | **kept** |

**(a) analysis.** Batch-24 improved ~26% (46.07 -> ~34.1 ms/signal) and cold improved ~58% (707 -> ~300 ms) — both clear wins, `cargo check`/`clippy -p t0-core -p t0-wasm --release --no-default-features --features t0-wasm/wgpu -- -D warnings` clean, `wasm-pack build ... --features wgpu` builds clean. Single-forecast warm latency is flat-to-slightly-worse (162.5 -> ~169.5, +4%, two repeat runs agree within 0.5ms of each other so this isn't just noise) — read as fusion's benefit being concentrated in cases with more distinct elementwise/reduction ops to amortize per call (batch path processes 2x more per-signal attention/FFN work per forward, cold path skips per-kernel-shape autotune the first few unfused kernels would otherwise separately trigger), while a single already-warm forecast has too little elementwise work relative to the big matmuls (dominant cost) for fusion to move the needle much. The `GpuChannel::Flush` CDP-event count (used as the dispatch-count proxy in the profiling step) went UP under fusion (58->105 single, 122->210 batch) despite wall-clock going down — this proxy evidently counts something other than compute-shader dispatches one-to-one (likely IPC-level flushes tied to fused-kernel shader-variant staging/compilation bookkeeping, not the underlying `dispatchWorkgroups` count), so wall-clock is treated as ground truth here, not the flush count. Net: kept because two of three measured numbers (cold, batch) improved substantially and the third (warm single) is within noise of the baseline, and the task brief's explicit tell for this change ("the batch-24 number is the tell") improved.

## Item 2b: intermediate readbacks

Verified by reading the whole forward path (`crates/t0-core/src/model.rs`),
not by tracing (the `gpu`/`blink.user_timing` CDP categories used here
don't surface `mapAsync` events by name, noted above): `forward_tensor`
never calls `.into_data()`/`.into_data_async()` on any intermediate
tensor (patch encoder, per-layer attention/FFN, out-norm, decoder,
quantile head all stay on-device); `forward_async` calls
`out.into_data_async().await` exactly once, on the final flattened
output tensor. Nothing to change here — already correct.

## Items 2c/2d: matmul autotune strategy / on-GPU Q8 dequant-matmul kernel

Not attempted this session. Reasoning: (a) already closed a substantial
fraction of the batch-24 gap (46->34 ms/signal) and the cold-start gap
(707->300ms) with a one-line feature-flag change and zero new code to
maintain; the remaining single-forecast warm gap (169ms ours vs 64ms
theirs) is dominated by matmul cost on 12 transformer layers at
context-512, and neither forcing a specific cubecl-wgpu matmul strategy
nor writing a custom on-GPU Q8 dequant-matmul kernel (reusing
`llm-web`'s `crates/llm-wasm/src/` Q8 kernels as reference per this
task's brief) is a small change — both are multi-hour efforts with real
correctness risk (a custom WGSL kernel needs numerical-parity
verification against the existing dequant-then-f32-matmul path before
it can be trusted, per this repo's own `ml-systems-burn-wgpu` standard).
Flagging as the next concrete step rather than attempting a rushed
version of either. Our current per-call warm latency (169ms, well above
the 80ms threshold the task brief names for triggering item (d)) means
this is not yet closed out — noted here rather than silently dropped.

## Item 2e: JS hot-path allocation/JSON

Checked `web/worker.js` (the production demo, not the bench harness):
the only `new Uint8Array`/`new Float32Array` allocations are in the
one-time model/series load path (lines 86, 127, 133), not inside the
per-forecast call. No JSON parsing in the hot path. Nothing to change.

## Summary: what was kept

Only item 2a (`burn-wgpu` `fusion` feature) was changed this session.
Final state vs baseline, same fixture/window as
`docs/runs/2026-09-20-head-to-head.md`:

| | cold ms | warm ms | batch-24 ms/signal |
|---|---|---|---|
| baseline (pre-fusion) | 707.1 | 162.5 | 46.07 |

| their ONNX INT8 (unchanged, WebGPU EP) | 167.5 | 64.0 | 8.87 |

Their per-call warm latency (64ms) and batch throughput (8.87 ms/signal)
are still ahead of ours after this session's change; the gap narrowed on
cold-start and batch, was flat on single-call warm. See
`docs/BENCHMARKS.md`'s head-to-head table for the full row including
accuracy columns and the honest "not yet faster and better simultaneously"
verdict.
