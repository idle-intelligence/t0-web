# t0-alpha (The Forecasting Company) — architecture, weights, license, and t0.run internals

## Summary

t0-alpha is a 101.6M-parameter (confirmed by direct tensor count, see below; card says "~102M") decoder-style patch transformer for probabilistic multivariate time-series forecasting, released Apache-2.0 by The Forecasting Company (TFC) on Hugging Face (`theforecastingcompany/t0-alpha`, [model card](https://huggingface.co/theforecastingcompany/t0-alpha)). It patches raw series into 32-step tokens, alternates 2 time-attention layers with 1 cross-variate ("group") attention layer (24 layers total, `group_every_n: 3`), and emits 5 native quantiles per output patch. Weights are plain F32 safetensors (411 MB total repo, one `model.safetensors` file), confirmed by inspecting the safetensors header directly. t0.run is a Vite/React SPA that runs ONNX exports of this model client-side via `onnxruntime-web`: **INT8** by default (107 MB download) on both WebGPU and WASM backends, with an **FP16** (208 MB) option toggle; weights are dequantized to FP32 for compute in both cases. Its on-page "past error lower/similar/higher" coloring is **not** CRPS/MASE — it's a simple ratio of live forecast MAE to a naive last-value-hold baseline MAE, computed per signal in the browser, not their published GIFT-Eval/fev-bench numbers. Data comes from Iowa Environmental Mesonet (METAR/ASOS) and NOAA Tides & Currents, proxied through a "shared cache" (not fetched directly from source in-browser). License is a clean Apache-2.0 grant with NOTICE attributions to Datadog's Toto and Amazon's Chronos-2 — no redistribution restriction found, but re-quantizing/rehosting is still an owner call given the NOTICE attribution obligations (see §2).

## 1. Model architecture

Source: `config.json` fetched directly from the repo ([raw](https://huggingface.co/theforecastingcompany/t0-alpha/raw/main/config.json)), the HF model card ([README](https://huggingface.co/theforecastingcompany/t0-alpha/blob/main/README.md)), the GitHub repo README ([theforecastingcompany/tfc-t0](https://github.com/theforecastingcompany/tfc-t0)), and a Towards Data Science architecture writeup ([Time-Series LLMs, Explained with t0-alpha](https://towardsdatascience.com/time-series-llms-explained-with-t0-alpha/)) — the TDS piece is a third-party explainer, not an official source, flagged as such below.

|---|---|---|
| Params | 101,641,541 (counted from safetensors header) | direct tensor inspection |
| Layers | 24 | config.json |
| `group_every_n` | 3 → 16 time-attention layers + 8 group(cross-variate)-attention layers | config.json + card |
| `embed_dim` | 512 | config.json |
| `mlp_hidden_dim` | 2048 (nominal); actual `mlp.0` weight is `[4096,512]` | config.json + tensor shapes (see §2, likely fused SwiGLU gate+up) |
| `num_heads` | 8 (head_dim 64, since `q_norm`/`k_norm` scale is `[64]` and `wQKV` is `[1536,512]` = 3×512) | config.json + tensor shapes |
| `patch_size` | 32 timesteps | config.json |
| `quantile_levels` | [0.1, 0.25, 0.5, 0.75, 0.9] | config.json |
| `scaler_use_arcsinh` | true | config.json |
| `dropout` | 0.1 | config.json |
| Attention type | Multi-head (not GQA) with QK-norm, causal within time-attention | tensor shapes (single `k_norm`/`q_norm` per layer sized to head_dim, not per-KV-group) — **not verified against source code**, inferred from weight shapes |
| Positional encoding | RoPE, applied only inside time-attention blocks ("time-aware rotary embeddings" per card); group-attention layers run over the variate axis and are described as not using RoPE | HF card + TDS piece — **not verified**: no `rope`/`freq` tensor exists in safetensors (RoPE is computed, not learned, so this is expected either way) |
| Normalization | Pre-norm RMSNorm (`norm.scale` vectors present, one per attention block and one per FFN block, no bias) | tensor shapes + card |
| FFN | SwiGLU-style (per card); `mlp.0.weight [4096,512]`, `mlp.2.weight [512,2048]` — the 4096-wide intermediate matches a fused gate+up projection (2×2048) then a SiLU-gated reduction to 2048 before the down-projection | tensor shapes; SwiGLU claim from HF card, shape math is my inference — **not verified** against actual module code |
| Patch encoding | Per-patch input dim 96 = patch_size(32) × 3 (value, time index, validity mask), an MLP with residual (`patch_encoder.projection.{mlp,residual_layer}`) into 512-dim tokens, plus a `type_embeddings` table of 3 rows × 512 (likely: target / historical covariate / future covariate) | tensor shapes; semantic labels for the 3 types are my inference — **not verified** |
| Output head | `decoder.mlp` (512→512→160) + `decoder.residual_layer` (512→160), 160 = 5 quantiles × 32-step patch, plus a fixed non-learned `head.quantile_levels` buffer `[5]` | tensor shapes |
| Context / horizon | Univariate `(B,T)`/`(T,)`, multivariate `(B,V,T)`; future covariates `(B,F,context+horizon)`; up to 1024 steps forecast in one forward pass, longer via autoregressive rollout | HF/GitHub card |
| Normalization scheme | Causal running mean/std with arcsinh transform on targets/history; global stats on future covariates | HF card |
| Training data | Not disclosed in card, repo, or README beyond "no dataset-specific feature engineering, no per-series tuning" (TDS characterization) — **not verified**, exact corpora unknown | TDS piece; card is silent |

t0-beta (256M params, embed_dim 1024, 21 quantile levels 0.01–0.99) is a separate, larger successor already on HF ([theforecastingcompany/t0-beta](https://huggingface.co/theforecastingcompany/t0-beta)) — not the model t0.run uses.

## 2. Weights, config, license

- **HF repo**: `theforecastingcompany/t0-alpha`, files: `model.safetensors` (407 MB, F32), `config.json` (250 B), `README.md`, `LICENSE`, `NOTICE`, `.gitattributes`. Total 411 MB. ([tree](https://huggingface.co/theforecastingcompany/t0-alpha/tree/main))
- **Dtype**: every one of 303 tensors in the safetensors header is `F32` — confirmed by fetching the file's 8-byte header-length prefix + JSON header via HTTP range requests against the HF CDN redirect (no full download needed). No bf16/fp16 in the canonical repo; those only exist in the separate ONNX exports.
- **Tensor names** (representative, per-layer pattern repeats identically for all 24 layers — the time/group distinction is behavioral, not structural; no separate weight class exists for group layers):
  - `patch_encoder.projection.mlp.{hidden_layer,output_layer}.{weight,bias}`, `patch_encoder.projection.residual_layer.{weight,bias}`, `patch_encoder.type_embeddings.weight [3,512]`
  - `transformer.layers.{i}.norm.scale [512]`, `.attention_block.norm.scale [512]`, `.attention_block.attention.wQKV.{weight [1536,512],bias [1536]}`, `.attention_block.attention.wO.{weight [512,512],bias [512]}`, `.attention_block.attention.{q_norm,k_norm}.scale [64]`, `.mlp.0.{weight [4096,512],bias [4096]}`, `.mlp.2.{weight [512,2048],bias [512]}`
  - `decoder.mlp.{hidden_layer,output_layer}.{weight,bias}`, `decoder.residual_layer.{weight [160,512],bias [160]}`, `head.quantile_levels [5]`
- **config.json** (full, verbatim): `dropout 0.1`, `embed_dim 512`, `group_every_n 3`, `mlp_hidden_dim 2048`, `num_heads 8`, `num_layers 24`, `patch_size 32`, `quantile_levels [0.1,0.25,0.5,0.75,0.9]`, `scaler_use_arcsinh true`. No tokenizer/scaler files ship separately — scaling is computed at runtime from causal statistics, not from a saved artifact.
- **License**: Apache License 2.0, full standard text ([LICENSE](https://huggingface.co/theforecastingcompany/t0-alpha/raw/main/LICENSE)). `NOTICE` file states: *"This product includes software developed at Datadog … licensed under the Apache License 2.0. Source: github.com/DataDog/toto"* and *"This product includes software derived from Chronos-2 by Amazon.com, Inc. … licensed under the Apache License 2.0. Source: github.com/amazon-science/chronos-forecasting"* ([NOTICE](https://huggingface.co/theforecastingcompany/t0-alpha/raw/main/NOTICE)). **Verdict (owner decision flagged, not mine to make)**: Apache-2.0 permits re-quantization and redistribution of derivative (quantized) weights commercially, provided the NOTICE file's attributions are carried forward in any redistribution and any modifications are stated (Apache-2.0 §4). No field-of-use or non-commercial clause found anywhere in LICENSE/NOTICE/README. The separate ONNX model cards (`t0-alpha-onnx-fp16`, `t0-alpha-onnx-int8`) additionally disclaim warranty on quantized accuracy ("recommend the full PyTorch model for production or consequential use") — this is a quality caveat, not a legal restriction.

## 3. t0.run: exact behavior (from live HTML + the shipped JS bundle)

Fetched `https://www.t0.run/` directly and downloaded/greped its main bundle `assets/field-CgkUepke.js` (7.4 MB, minified) for literal strings — this is source-of-truth over any description, since the page is a client-rendered SPA with no server-rendered content.

- **Page meta**: title "Forecast Field — The Forecasting Company"; og:description: *"Explore, forecast and backtest 1,000 real-world signals on your own device. Powered by t0-alpha and WebGPU."*
- **Runtime backend selection** (from bundle): `useState(() => matchMedia('(pointer: coarse)').matches || !('gpu' in navigator) ? 'wasm' : 'webgpu')` — i.e., WebGPU is the default whenever `navigator.gpu` exists and the pointer isn't coarse (touch); phones fall back to WASM. Model **precision defaults to `'int8'`** (`useState('int8')`) regardless of backend; a settings toggle lets the user switch to FP16 ("Choose the data collection, spatial zoom from 0.1 to 1.4, and INT8 or FP16 model. If automatic forecasts are on, changing model downloads that edition once (107 or 208 MB)…" — literal string in bundle).
- **Model files referenced**: links to `https://huggingface.co/theforecastingcompany/t0-alpha-onnx-{fp16|int8}` directly from the UI, with sizes shown in-app as "107 MB" (int8) / "208 MB" (fp16) — matching the HF-hosted ONNX artifacts `t0-alpha-grouped-int8.onnx` (107.2 MB) and `t0-alpha-grouped-fp16.onnx` (208.1 MB).
- **ONNX runtime details** ([t0-alpha-onnx-int8 card](https://huggingface.co/theforecastingcompany/t0-alpha-onnx-int8), [t0-alpha-onnx-fp16 card](https://huggingface.co/theforecastingcompany/t0-alpha-onnx-fp16)): opset 20; INT8 card states "per-channel signed INT8 weight quantization with FP32 activations… weights are stored in INT8, while calculations and expanded runtime weights use FP32" (i.e., dequantize-then-matmul-in-FP32, not true int8 GEMM); FP16 card says weights stored FP16, "runtime calculations use FP32". Both note an accompanying `webgpu-options.js` that "keeps mask operations on WASM while folding constant weight expansion for WebGPU." Both validated against `onnxruntime-web` 1.29.0, Chromium 152, Apple Metal 3 (per fp16 card fetch) — **not independently re-verified**, taken from card text. I could not find the literal `onnxruntime-web` string inside the bundle itself (it may be inlined/renamed by the bundler); this inference rests on the model cards, not a confirmed import in the JS.
- **Data source**: bundle contains literal endpoints `https://mesonet.agron.iastate.edu/sites/site.php` (Iowa Environmental Mesonet — the standard public ASOS/METAR archive) and `https://tidesandcurrents.noaa.gov/stationhome.html`, plus domain tags `air_temperature`, `wind_speed`, `water_level`, `water_temperature`, `electricity` in the code — **the demo is not METAR-only**; it spans weather (METAR/ASOS), NOAA tide/water stations, and at least one `electricity` signal domain. GOAL.md's "~1000 METAR signals" framing is only partially accurate: METAR is one of several signal families, not verified to be the majority. Observations are fetched from `${API_BASE}/observations/v1/${id}.json` against what the UI itself calls a "shared cache" ("Observations come from a shared cache. Forecasts run on your device." — literal string), i.e. TFC proxies/caches the upstream sources server-side rather than the browser hitting Mesonet/NOAA directly.
- **Context lengths / windows actually used**: bundle contains cached example keys like `fp16:120:solo:27`, `int8:144:joint:24`, `fp16:168:joint:11` — i.e., three context lengths in active use: **120, 144, 168** timesteps, and two multivariate modes **`solo`** (univariate) vs **`joint`** (multi-signal/covariate). These look like pre-baked example/preview forecasts embedded in the bundle for cold-start display, not necessarily the live backtest parameters — **not fully verified** whether 120/144/168 are also the live "Forecast all" context lengths or just these cached preview keys.
- **Error metric ("past error lower/similar/higher")**: found the exact computation in the bundle:
  ```
  function(...){ ...; return {mae: o?i/o:null, baselineMae: o?a/o:null, samples:o} }
  function Kt(e){ if(!e||e.mae===null||e.baselineMae===null||!e.samples) return 'unknown';
    if(e.baselineMae<1e-8) return e.mae<1e-8?'similar':'worse';
    let t=e.mae/e.baselineMae; return t<.8?'better':t>1.2?'worse':'similar' }
  ```
  i.e. **mae** = mean absolute error of the model's past forecasts vs realized observations; **baselineMae** = MAE of a naive "hold last value" persistence forecast over the same points; tone = `mae/baselineMae`: **<0.8 → green/"lower" (better)**, **>1.2 → amber/"higher" (worse)**, else grey/"similar". UI copy confirms: *"Cell colours compare past forecast error with holding the last value: green is lower, grey is similar, amber is higher."* This is a live, per-signal, browser-computed metric — **it is not CRPS or MASE**, and is unrelated to the GIFT-Eval/fev-bench numbers on the model card. No "Forecast all" timing numbers are published anywhere I found (card, GitHub, blog, or bundle strings) — **not verified/not published**.
- **Published accuracy** (from HF card, not from t0.run): GIFT-Eval ([SalesforceAIResearch/gift-eval](https://github.com/SalesforceAIResearch/gift-eval), 97 configs / 55 datasets / 7 domains) CRPS 0.4941, MASE 0.7240 (normalized to seasonal-naive); fev-bench ([arXiv:2509.26468](https://arxiv.org/pdf/2509.26468), 100 tasks) skill score 42.2. The exact eval protocol (per-dataset splits, context/horizon per task, aggregation formula) is defined by the GIFT-Eval and fev-bench repos themselves, not by TFC — **not independently reproduced here**; TFC's card only reports the aggregate scores, not per-dataset breakdowns.

## 4. Reference implementations & comparisons

- **Official code**: [github.com/theforecastingcompany/tfc-t0](https://github.com/theforecastingcompany/tfc-t0) — PyTorch (`tfc-t0` PyPI package), plus an MLX port (`tfc-t0-mlx`, "inference-only, loads same safetensors") for Apple Silicon. No GGUF. ONNX exports (fp16/int8) are official, hosted as separate HF repos, not community conversions. No Rust/Burn/candle port found anywhere (searched HF, GitHub, PyPI) — **not verified to not exist, but none surfaced**.
- **NOTICE-acknowledged lineage**: Datadog's [Toto](https://github.com/DataDog/toto) and Amazon's [Chronos-2](https://github.com/amazon-science/chronos-forecasting), both Apache-2.0, are explicitly named as sources of derived code; NXAI's TiRex is credited in the HF card text for "architectural innovations" (patch masking) but not in NOTICE, so likely inspiration rather than derived code.
- **Comparisons** (from HF card + TDS piece, not independently benchmarked here):
  - **Chronos-2**: T5-style encoder-decoder, discretizes values into token bins; t0-alpha is decoder-only and regresses continuous quantiles directly — no shared tokenization scheme despite the NOTICE credit.
  - **TimesFM**: also patch-based decoder-only, closest architectural sibling; TFC's card doesn't detail exact divergences beyond quantile head vs TimesFM's own head.
  - **Moirai**: masked-encoder (not causal decoder), handles arbitrary variate counts via a different mechanism than t0-alpha's fixed group-attention-every-3-layers scheme.
  - **Toto**: direct code lineage per NOTICE; likely shares patch/scaler/attention primitives most closely of any peer, though exact overlap wasn't diffed here.
  - **TiRex**: much smaller (35M vs 101.6M), reported slightly ahead on aggregate CRPS per TDS piece — gap "within run-to-run variation."

## 5. Feasibility for a Burn/wgpu port

Tensor-level plan (uses tensor names from §2 directly):

- **Reuse from llm-web**: safetensors loader, RMSNorm kernel (matches `norm.scale`/`attention_block.norm.scale`, no bias, so a bias-free RMSNorm op), generic MHA/attention dispatch with QK-norm support (need to confirm llm-web's attention kernel supports a q/k normalization step — Qwen2 doesn't use it, so this may be new), RoPE kernel (needs a variant that's applied conditionally — only on time-attention layers, not group layers), SwiGLU-style gated FFN kernel (if fused gate+up in one matmul of width 4096 splitting into two 2048 halves — confirm this matches llm-web's existing SwiGLU shape assumptions or needs a variant), Q8/Q4 WGSL dequant+matmul kernels for the big `wQKV`/`wO`/`mlp.0`/`mlp.2` weights.
- **New for this model**: patch embedding (`patch_encoder.projection`, input dim 96 = 32×3, MLP+residual, this is not a lookup-table embedding, no equivalent in llm-web today), `type_embeddings` lookup (3 rows), the group-attention reshape (transpose batch/variate axis into the sequence dim every 3rd layer per `group_every_n`), the causal-running-stats + arcsinh scaler (not a saved artifact — must be implemented, not loaded), and the quantile output head (`decoder.mlp` + `decoder.residual_layer` producing 160 = 5×32 values per patch, need de-patching/reshape into (5, horizon)).
- **KV cache**: only meaningful for time-attention layers during autoregressive rollout beyond 1024 steps; group-attention layers operate over the (small, ≤ few hundred) variate axis per patch-step and likely need no cache — **not verified**, no rollout code was inspected (PyPI package internals not fetched, out of scope for this pass).
- **Quantization ladder**: safest to quantize the large per-layer matmuls — `wQKV` (1536×512), `wO` (512×512), `mlp.0` (4096×512), `mlp.2` (512×2048) — to Q8 then Q4, following the ONNX int8 card's own precedent of "per-channel signed INT8" (i.e. per-output-channel scale, not per-tensor). Per the TFC int8 card, they keep some projections FP32 "to preserve extreme quantiles" but the card doesn't name which six — **not verified which specific tensors**, worth checking the actual ONNX graph's weight dtypes directly (out of scope for this pass; would need to open the `.onnx` file, not just read the card). Candidates to keep at F16/F32 by default: `decoder.mlp.output_layer`/`decoder.residual_layer` (produce the quantile values directly — precision-sensitive per the int8 card's own caveat), `patch_encoder.*` (small, cheap, and gates all downstream accuracy), `q_norm`/`k_norm`/`norm.scale` (tiny, must stay full precision), `head.quantile_levels` (a fixed constant buffer, not a weight).
- **Backtest protocol to reproduce "matches within noise"**: GOAL.md's "Q4 size, equal error to their published backtest" needs the *GIFT-Eval* protocol specifically (their headline published number: CRPS 0.4941 / MASE 0.7240), not t0.run's live MAE-vs-persistence tone metric — those are different measurements on different data. To reproduce: pull [SalesforceAIResearch/gift-eval](https://github.com/SalesforceAIResearch/gift-eval)'s 97 task configs (55 datasets, 7 domains, per-task context/horizon/frequency as defined by that repo), run t0-alpha's own eval harness (in `tfc-t0` if present — **not confirmed to include an eval script**, needs a code read of the PyPI/GitHub package) or reimplement CRPS/MASE aggregation per GIFT-Eval's own formula, and compare against the published 0.4941/0.7240 at matching quantization. Separately, if the goal is to also beat/match the *t0.run-visible* number, that requires the METAR/NOAA "shared cache" observation history (station list + fetch path, per GOAL.md pointing at trucs.ai `knn-weather`) and reimplementing the exact `mae/baselineMae` ratio above, on the same 120/144/168-step context lengths seen in the bundle.

## 6. Open questions / owner decisions

- **Owner decision**: re-quantizing and redistributing t0-alpha weights publicly is permitted by Apache-2.0 (with NOTICE carried forward), but publishing a public demo/HF upload of quantized weights is a call for the maintainer per the project's own rule ("stop and report on any owner decision: license terms, publishing, HF uploads, naming").
- Which six tensors the official INT8 ONNX export keeps at FP32 — not stated in the card; would need to open the `.onnx` graph directly.
- Whether SwiGLU's gate/up split in `mlp.0` (4096→split into two 2048 halves) matches an activation llm-web's kernels already support, or needs a new WGSL variant — not confirmed, no source code for the FFN forward pass was read (PyPI/GitHub Python source wasn't opened in this pass).
- Whether RoPE is truly absent from group-attention layers, and what "time index" scalar is fed into the patch encoder (raw timestamp? relative step counter? per-frequency encoding?) — asserted by the HF card/TDS piece but not confirmed against source.
- Exact composition of the "~1000 signals": how many are METAR/ASOS vs NOAA tide/water vs `electricity`, and the exact station list — GOAL.md assumes ~1000 METAR; the bundle shows multiple signal domains, so this needs a direct count against the "shared cache" observations endpoint (not accessible without a browser session/likely an API key, not attempted here).
- Whether `tfc-t0`'s PyTorch package ships its own GIFT-Eval/fev-bench harness or whether TFC's published numbers were produced with a private eval script — not confirmed; would require reading the PyPI package source.
- No published "Forecast all" wall-clock timing anywhere found — the "beat their numbers on speed" goal in GOAL.md has no public baseline to beat; we'd only be racing our own measurement, not a disclosed TFC number.
